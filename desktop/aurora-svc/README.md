# aurora-svc

The privileged helper for Aurora's Windows and Linux desktop builds. The desktop app routes all traffic through a TUN device, which needs elevated rights. So that connecting and disconnecting never prompts for UAC or sudo, the privileged work (start and stop the official `sing-box`) lives in a service installed once: a Windows service `AuroraSvc` running as LocalSystem, or a systemd unit on Linux. The Flutter app talks to it over local HTTP only.

## API

Listens on `127.0.0.1:53421` only, with Bearer-token authentication.

| Method | Path | Description |
|---|---|---|
| POST | `/start` | body `{"config": "<sing-box JSON>", "clash_probe": {...}, "owner_pid": <int>}`. The body carries the config itself, not a path |
| POST | `/stop` | Stop the sing-box child process (graceful first, see below) |
| GET | `/status[?owner_pid=<int>]` | `{"state":"running\|stopped\|error","detail":"<on failure, sing-box's own last two lines>"}` |
| GET | `/diagnose` | The interface table, whether `aurora0` exists, who owns the tunnel, and the core's full log tail |

`/start` is idempotent: repeating the same config does not disturb the tunnel. A changed config restarts with the new one (answering 200 while keeping the old tunnel would leave the user on a route they did not choose).

`/start` is a three-stage handshake: preflight (binary and `wintun.dll` present, `sing-box check` on the config, a short wait for any leftover `aurora0` to go away), launch, then a readiness wait that polls the child and the Clash API's `/version`. The readiness budget is 45 seconds and must stay well above 10 seconds, which is sing-box's own patience for the Windows adapter install. A start that never saw the interface come up is tagged `tun_interface_never_up`; one that began from a leftover adapter is tagged `stale_adapter_adopted`. The app matches on these tokens, so do not change them.

### Tunnel owner (`owner_pid`)

`owner_pid` means "stop the tunnel when this process is gone". The GUI sends its own pid. `aurora-cli` deliberately does not, because it connects and exits and its tunnel must outlive it. The same query parameter on `/status` re-claims ownership: when the app restarts and adopts a tunnel that outlived it, ownership has to follow, or the tunnel would point at a pid that no longer exists.

Omitting the field keeps the old behaviour entirely, so an old app works with a new service. On Windows the service holds a real process handle (`OpenProcess(SYNCHRONIZE)`), so pid reuse cannot fool it.

### Stop asks before it kills

All of sing-box's cleanup (removing the TUN device, routes, firewall state, flushing DNS) happens in its own signal handler. So `/stop` sends SIGTERM (Linux) or CTRL_BREAK (Windows), waits 3 seconds, and only then kills. Both paths end with a system DNS cache flush, which is the one thing a killed core can never do for us and the direct cause of "the network is still wrong after I quit the app".

Sending a console event on Windows needs a console, and a service has none, so the service allocates its own (invisible, session 0). If that fails, stop falls back to a hard kill, exactly as before, so it never becomes unable to stop.

### Responses are always UTF-8

`/status` and `/diagnose` declare `charset=utf-8` explicitly. Windows adapter FriendlyNames are localized, and failure details contain localized Win32 error strings. Dart's `http` package decodes a response with no charset as latin-1, which produces mojibake, and the user picks an interface name from the `/diagnose` list and sends it back to the core. A mangled name is a name sing-box will never resolve.

## Why the config is sent, not a path

The service runs as LocalSystem and the app as the logged-in user. Per-user variables (`%APPDATA%`, `%USERPROFILE%`, `%TEMP%`) resolve to different directories in the two processes, so any location derived from them and "agreed" by both sides cannot match. That was the cause of every connect failing with `403 config path outside allowed dir`.

Callers now hand over bytes, and the privileged side writes them into its own directory and runs from there. This removes that class of bug, along with the time-of-check/time-of-use gap between writing and reading. Shared locations are derived only from machine-wide variables (`%ProgramData%`, then `%ALLUSERSPROFILE%`); `TestResolvePathsNeverReadsPerUserEnv` in `paths.go`'s tests guards this rule. On Linux the state directory is hard-coded to `/var/lib/aurora` for the same reason.

## On-disk layout (Windows)

| Path | Content | Permissions |
|---|---|---|
| `%ProgramData%\Aurora\svc-token` | Shared Bearer token (generated by the service) | Writable by SYSTEM and administrators, readable by local users |
| `%ProgramData%\Aurora\run\` | The `config.json` the service wrote and ran, sing-box's `cache.db` | SYSTEM and Administrators only (explicit DACL, inheritance from ProgramData cut) |
| `%ProgramData%\Aurora\logs\sing-box.log` | Child stdout/stderr (overwritten on each start) | Readable by users, for troubleshooting |
| `%ProgramData%\Aurora\logs\aurora-svc.log` | The service's own install, start/stop and failure log | Same |

## Security boundary

- Listens on `127.0.0.1` only, and a token is required. With no token configured, every request is refused.
- The token is read on every request. The service starts at boot and the token may be written or rotated afterwards; caching it would mean 401s until restart.
- On Windows the child is placed in a kill-on-close Job Object. However the service disappears (crash, kill, uninstall), Windows takes sing-box with it, so no unmanaged TUN keeps capturing the machine's traffic.
- The service only manages process lifetime. Status, traffic and route selection go from the app straight to sing-box's Clash API, not through this service.

```bash
# Logic tests run on any OS (including the 403 regression test):

```

## Subcommands (Windows)

```
aurora-svc.exe install     # register as an auto-start service (LocalSystem) and start it; if already registered, repoint to this exe and restart
aurora-svc.exe uninstall   # stop and delete the service, wait for aurora0 to vanish, flush DNS, remove machine-wide state
aurora-svc.exe run         # invoked by the SCM; run with no arguments it serves HTTP in the foreground (manual debugging)
```

`install` must repoint rather than skip when the service already exists. An old unpacked install registers the service at whatever directory the user extracted to; once that is deleted or upgraded, the service points at a missing exe and can never start again.

`uninstall` is more than `DeleteService`, and both pitfalls are silent. While anyone holds an open handle to a service (services.msc parked on the row, a monitoring agent enumerating services), `DeleteService` only marks it for deletion and the service stays listed until the last handle closes. Calling it on a service that has not fully stopped fails outright. So the sequence is: wait for STOPPED, retry the delete, then after closing our own handle check again and say plainly that the service will disappear only after a reboot, rather than reporting success. Whether or not the delete succeeds, machine-wide state (the shared token, the last plaintext `config.json` the service ran, logs) is removed: a crippled service that cannot start should not keep credentials on disk.

## Linux

The same binary runs as a systemd service (`aurora-svc.service`, root, `AmbientCapabilities=CAP_NET_ADMIN CAP_NET_RAW`). `install` and `uninstall` write and remove the unit and run `systemctl enable --now`; the bare or `run` invocation just serves HTTP, since systemd owns the process lifecycle. State lives in `/var/lib/aurora`.
