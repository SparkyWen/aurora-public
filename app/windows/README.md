# Aurora for Windows: install, build, package, troubleshoot

## Architecture in one paragraph

Flutter compiles the contract into sing-box JSON and hands **the configuration
itself** over a local HTTP API (token-authenticated) to `aurora-svc` (a Windows
service, installed by the installer), which starts the official `sing-box.exe`
(TUN + `wintun.dll`) with privileges. Flutter talks directly to sing-box's Clash
API (a per-connection random loopback port and secret) to read status, traffic and
node latency, and to switch nodes. The TUN captures all traffic.

## Installing (user view)

Download **`aurora-<tag>-windows-x64-setup.exe`** from the Release, double-click,
accept one UAC prompt, and click through.

Once the installer finishes, it **works immediately**; there is nothing to set up
in the app:

- It installs into `C:\Program Files\Aurora` (writable only by administrators; the
  privileged service runs the `sing-box.exe` in there, and installing it into a
  user-writable directory would hand out SYSTEM privileges).
- It registers and starts the `AuroraSvc` service as administrator, so everyday
  connect/disconnect **never raises UAC**.
- It creates Start menu and desktop shortcuts. An upgrade stops the app and the
  service before overwriting; an uninstall stops and removes the service and
  deletes `C:\ProgramData\Aurora` and the per-user data.

> The installer has no code-signing certificate, so SmartScreen will warn:
> **More info -> Run anyway**.

The portable zip (`...-windows-x64-portable.zip`) is only for when the installer
fails: after unpacking, install the service yourself from the app's settings, and
do not unpack into a directory that will be deleted later (the service remembers
the path).

## Troubleshooting (look in this order when it will not connect)

| What to look at | Where |
|---|---|
| sing-box's own failure reason | `C:\ProgramData\Aurora\logs\sing-box.log` |
| the service's own start/stop/install log | `C:\ProgramData\Aurora\logs\aurora-svc.log` |
| connection and path-decision timeline | `%APPDATA%\Aurora\path-events.jsonl` |
| is the service running | `sc query AuroraSvc` |
| which exe the service points at | `sc qc AuroraSvc` (after an upgrade it should point into `C:\Program Files\Aurora`) |

The app's settings page shows whether the service is running; if it is broken, use
the repair action (it re-points the registration at the current program and
restarts it, with one UAC prompt).

**`tun_interface_never_up` in a connection failure** (the log tail usually also has
sing-box's `open interface take too much time to finish!`): this is neither the
configuration nor the network. Creating the wintun virtual adapter did not finish
within 45 seconds. It is really a device installation, and it stalls when security
software hooks device installs, or when a previous adapter is stuck in the system.
Reboot first; if it keeps happening, temporarily turn off the security software's
network protection and reconnect. See `docs/reliability-notes.md`.

## Prerequisites (developers)

- Flutter >= 3.44 (Dart ^3.12.1) and Visual Studio (Desktop C++ workload).
- Place the three packaging components in `app/windows/aurora-svc/` (see the README
  there):
  - `sing-box.exe` (official 1.13.14 amd64)
  - `wintun.dll` (official wintun package)
  - `aurora-svc.exe` (`cd desktop/aurora-svc && GOOS=windows GOARCH=amd64 go build -o ../../app/windows/aurora-svc/aurora-svc.exe ./...`)
- Public builds embed no contract; the app starts empty and you add a server by
  importing an `aurora://` link. A private fork may embed a contract at
  `app/assets/configs/aurora-contract.json` (gitignored, never committed).

## Build

```bash
cd app
flutter pub get
flutter test                          # compiler windows platform + Clash/svc client tests
flutter build windows --release
```

Output: `build/windows/x64/runner/Release/aurora.exe` (components in the same
directory).

To build the installer (needs Inno Setup 6, which CI installs automatically):

```powershell
& "${env:ProgramFiles(x86)}\Inno Setup 6\ISCC.exe" `
  /DAppVersion=1.0.0 `
  "/DSourceDir=$(Resolve-Path app\build\windows\x64\runner\Release)" `
  "/DOutputDir=$(Get-Location)" `
  /DOutputBase=aurora-windows-x64-setup `
  app\windows\installer\aurora.iss
```

The installer is English only. On a `v*` tag, `.github/workflows/release.yml`
builds all of this and attaches it to a draft Release; publish the draft after
checking the exact installer package. When Windows-related files change,
`.github/workflows/windows-check.yml` first runs the aurora-svc unit tests, a
`GOOS=windows` build, and checks that the installer script compiles.

## Security boundaries

- `aurora-svc` listens only on `127.0.0.1:53421` and compares the Bearer token in
  constant time. The token is at `C:\ProgramData\Aurora\svc-token` and is
  **generated by the privileged side** (DACL: SYSTEM/administrators can write,
  local users read-only); both sides **read it fresh on every request** and do not
  cache it.
- **`/start` carries the configuration content, not a path.** The privileged
  process never accepts a caller-specified file location: it writes the received
  JSON into its own `C:\ProgramData\Aurora\run\` (DACL tightened to SYSTEM +
  Administrators) and runs that. This closes the context mismatch behind the old
  `403 config path outside allowed dir` failure, and also the time-of-check gap
  where a file could be swapped between being written and being read.
- The sing-box child process is bound into a kill-on-close Job Object: however the
  service goes away, the tunnel goes with it, so no unmanaged TUN is left behind.

## Acceptance checklist

After testing on a real Windows machine, check: the exit IP, fail-closed behavior,
no UAC prompt for everyday use, upgrade-in-place, and a clean uninstall.
